## Analysis: Registry Implementation vs. UC-02 PID/Attestation Provider Onboarding Requirements

This document analyzes the current Member State Registry implementation against the UC-02 requirements for PID/Attestation Provider onboarding.

---

## ✅ IMPLEMENTED (Aligned with Requirements)

| Requirement | Status | Implementation |
|-------------|--------|----------------|
| **Entity Roles** | ✅ | `EntityRole` enum: `PID_PROVIDER`, `ATTESTATION_PROVIDER`, `RELYING_PARTY` |
| **Entitlement Types** | ✅ | `EntitlementType` enum: `QEAA_Provider`, `PUB_EAA_Provider`, `Non_Q_EAA_Provider`, `PID_Provider`, `Service_Provider`, `Intermediary` |
| **Identifier Types (CIR Annex I)** | ✅ | `IdentifierType`: `EUID`, `VAT_NUMBER`, `LEI`, `EORI`, `NATIONAL_BUSINESS_REG`, etc. |
| **Legal Entity with Address** | ✅ | `LegalEntity`, `LegalPerson`, `NaturalPerson`, `PhysicalAddress` models |
| **Registration Status** | ✅ | `RegistrationStatus`: `pending`, `active`, `suspended`, `revoked` |
| **Supervisory Authority (DPA)** | ✅ | `SupervisoryAuthority` model with contact info |
| **Registry URI** | ✅ | `RegisteredEntity.registry_uri` - National registry API URI |
| **Public Sector Body flag** | ✅ | `RegisteredEntity.is_psb` for PuB-EAA Providers |
| **Intermediary support** | ✅ | `is_intermediary`, `EntityUsesIntermediary` relationship |
| **Service Descriptions (multilingual)** | ✅ | `EntityServiceDescription` with language codes |
| **Entitlements** | ✅ | `EntityEntitlement` with ETSI URIs and dates |
| **Attestation types (for issuers)** | ✅ | `EntityProvidesAttestation` with `Credential` model |
| **Intended Use (for verifiers)** | ✅ | `IntendedUse`, `IntendedUseCredential`, `IntendedUsePurpose` |
| **Privacy Policies** | ✅ | `Policy`, `IntendedUsePrivacyPolicy`, `RegisteredEntityPolicy` |
| **Credential Formats** | ✅ | `CredentialFormat`: `sd-jwt-vc`, `dc+sd-jwt`, `mso_mdoc`, etc. |
| **Access Certificates** | ✅ | `EntityAccessCertificate` with CT log support (RFC 9162) |
| **Registration Certificates** | ✅ | `EntityRegistrationCertificate` model |
| **Trusted Lists (ETSI TS 119612)** | ✅ | `TSLScheme`, `TrustServiceProvider`, service type URIs for EUDI Wallet entities |
| **Audit Timestamps** | ✅ | `created_at`, `updated_at` on all models |

## ⚠️ PARTIALLY IMPLEMENTED (Needs Enhancement)

| Requirement | Gap | Recommendation |
|-------------|-----|----------------|
| **10-year Record Keeping** | Missing explicit history tables | Add `RegistrationHistory`, `CertificateHistory` models or enable Django simple history |
| **Qualification Evidence (QEAA)** | Not explicitly modeled | Add `QEAAQualificationEvidence` model |
| **Public Sector Body Evidence (PuB-EAA)** | Only boolean flag | Add `PSBEvidence` model with authority references |
| **Certificate Revocation Status API** | Models exist but no dedicated endpoint | Add `/certificates/{id}/status` API endpoint |
| **Suspension/Cancellation reasons** | `revocation_reason` exists for certs, not for registration | Add `suspension_reason`, `cancellation_reason` to `RegisteredEntity` |

---

## ❌ NOT IMPLEMENTED (Missing Features)

| Requirement | UC-02 Section | Description |
|-------------|---------------|-------------|
| **Notification to EC** | 2.7 | No workflow for MS → EC notification |
| **Automatic Registry Monitoring** | 3.1 | No scheduled jobs to monitor certificate validity |
| **24-hour Revocation Processing** | 3.4 | No SLA enforcement mechanism |
| **Certificate Transparency v2.0 Logging** | 2.3 | Fields exist but no CT log integration |
| **OpenAPI v3 specification** | Annex II | No OpenAPI schema generated |
| **JSON Web Signature/Seal on API responses** | Annex II | API responses not signed |
| **Audit Log Model** | 3.1 | `AuditLog` imported but not visible in models |
| **Registration Certificate JWT format** | 2.6 | Certificate stored as PEM, not JWT (rc-wrp+jwt) |
| **General Access Policy** | 2.6 | Missing per Article 8(3) |
| **EU-level TL compilation** | 2.8 | Only MS TL - no EC LoTL integration |

## Recommendations

### High Priority (Regulatory Compliance)

1. **Add OpenAPI schema** - Required per Regulation (EU) 2025/848 Annex II(2)(d)
2. **Implement JSON signing for API responses** - Per Annex II(1) - electronically signed or sealed JSON files
3. **Add notification workflow model** - Track MS → EC notifications for PID/PuB-EAA Providers
4. **Implement registration certificate in JWT format** - Per ETSI TS 119 475 (rc-wrp+jwt)

### Medium Priority (Operational)

5. **Add audit/history tracking** - 10-year record keeping per Article 10
6. **Add suspension/cancellation workflow** - With 24h SLA fields per Article 9(5)
7. **Add qualification evidence models** - For QEAA/PuB-EAA verification per Annex I

### Lower Priority (Enhancement)

8. **CT log integration** - Already has fields, needs backend integration
9. **Automated monitoring jobs** - Celery tasks for certificate validity checks

---

## Overall Assessment

The registry covers **approximately 80% of the UC-02 data model requirements**. 

The main gaps are in:
- **Signed API responses** (JSON Web Signature) - Required for interoperability
- **Notification workflow to EC** - Required for PID/PuB-EAA Provider publication
- **Registration certificate JWT format** - Per ETSI TS 119 475
- **Automated monitoring/SLA enforcement** - 24-hour revocation processing

### Coverage by UC-02 Phase

| Phase | Coverage | Notes |
|-------|----------|-------|
| **1. Administrative Onboarding** | ~90% | Registration data model complete |
| **2. Technical Onboarding** | ~70% | Certificate models exist, missing JWT format and notification workflow |
| **3. Post-Onboarding** | ~50% | Status fields exist, missing monitoring/SLA automation |
