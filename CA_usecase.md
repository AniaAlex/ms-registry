# CA Use Cases: Registry Response Signing

## Overview

The ms-registry API returns JWS-signed responses so that API clients (Wallet Units, verifiers) can cryptographically verify that the data came from a legitimate registry operator and has not been tampered with in transit.

The registry operator holds a **private signing key**. The corresponding public key is either:
- Self-issued and published directly (no CA involved), or
- Wrapped in an **X.509 certificate** signed by a Certificate Authority

This document describes Use Case 1: the CA-backed certificate model.

---

## Use Case 1: Registry Operator with CA-Issued Signing Certificate

### Context

A Member State authority operates the national WRP registry. The authority obtains a signing certificate from the national PKI (or the EU Trust Anchor PKI). Wallet Units are pre-loaded with the trusted root CA certificate, so they can verify any registry response signed under that chain without needing to know the registry's specific key in advance.

---

### Actors

| Actor | Role |
|---|---|
| Member State Registry Operator | Runs ms-registry, holds the private signing key |
| National CA (or EU Trust Anchor) | Issues the signing certificate to the registry operator |
| Wallet Unit | Queries `/wrp`, verifies the JWS signature on the response |
| Relying Party | Sends a presentation request to the Wallet Unit |

---

### Flow

```
National CA
│
│  (1) Registry operator generates key pair (EC P-256)
│  (2) Operator submits CSR (Certificate Signing Request) to CA
│  (3) CA issues X.509 certificate binding the operator's public key
│      to its identity (e.g. "SE National WRP Registry")
│
└── Issues certificate to ──► Registry Operator
                                │
                                │  Stores in:
                                │  - Private key → environment secret / HSM
                                │  - Certificate chain → served at /jwks or /.well-known
                                │
                                │  (4) Wallet Unit queries /wrp
                                │
                                ▼
                           ms-registry API
                                │
                                │  (5) Builds JSON response payload
                                │  (6) Signs payload with private key → JWS
                                │  (7) Returns JWS compact serialization
                                │
                                ▼
                           Wallet Unit
                                │
                                │  (8) Extracts certificate from JWS header (x5c)
                                │  (9) Verifies certificate chain up to trusted root CA
                                │  (10) Verifies JWS signature using the certificate's public key
                                │  (11) Trusts the WRP data in the payload
                                │
                                ▼
                     Wallet accepts or rejects
                     the Relying Party's request
```

---

### JWS Structure

The signed response is a **JWS Compact Serialization**:

```
BASE64URL(Header) . BASE64URL(Payload) . BASE64URL(Signature)
```

**Header example:**
```json
{
  "alg": "ES256",
  "typ": "JWT",
  "kid": "se-registry-signing-key-2026",
  "x5c": [
    "<base64-encoded DER leaf certificate>",
    "<base64-encoded DER intermediate CA certificate>"
  ]
}
```

- `alg: ES256` — ECDSA with P-256 curve and SHA-256 (recommended for EUDI ecosystem)
- `x5c` — the certificate chain, so the verifier can validate it against the trusted root
- `kid` — key identifier for cache/lookup purposes

**Payload example:**
```json
[
  {
    "identifier": "SE-WRP-00123",
    "legalname": "Example Bank AB",
    "tradename": "ExBank",
    "isintermediary": false,
    "entitlements": ["http://data.europa.eu/eudi/entitlement/Service_Provider"],
    ...
  }
]
```

**Signature:** computed over `BASE64URL(Header).BASE64URL(Payload)` using the registry operator's EC P-256 private key.

---

### What the Registry Needs

| Component | Description |
|---|---|
| EC P-256 private key | Generated by the registry operator, never leaves the server (ideally stored in an HSM or secrets manager) |
| X.509 leaf certificate | Issued by the national CA, binds the operator's public key to its identity |
| Intermediate CA certificate (if any) | Included in the `x5c` chain in the JWS header |
| Trusted root CA certificate | Pre-installed in Wallet Units as a trust anchor — not sent in the JWS |
| JWKS endpoint (optional) | `GET /.well-known/jwks.json` — publishes the current public key so clients can also verify without `x5c` |

---

### What the Wallet Unit Needs

| Component | Description |
|---|---|
| Trusted root CA certificate | Pre-loaded into the wallet as a trust anchor (distributed as part of the EUDI trust framework) |
| JWS verification library | Standard library to validate the signature (e.g. using the JOSE standard) |

---

### Implementation Notes for ms-registry

To implement this use case, the following would be added to the codebase:

1. **Settings** — load private key and certificate chain from environment variables or a secrets manager:
   ```python
   # settings.py
   REGISTRY_SIGNING_KEY = env("REGISTRY_SIGNING_PRIVATE_KEY_PEM")
   REGISTRY_SIGNING_CERT_CHAIN = env("REGISTRY_SIGNING_CERT_CHAIN_PEM")
   ```

2. **Signing utility** — a helper that takes a Python dict and returns a signed JWS string:
   ```python
   # utils/signing.py
   def sign_response(payload: dict) -> str:
       # Load private key and cert chain
       # Build JWS header with x5c
       # Sign and return compact serialization
       ...
   ```

3. **Views** — each `/wrp` GET handler wraps its response through the signing utility before returning.

4. **JWKS endpoint** — `GET /.well-known/jwks.json` returns the registry's current public key in JWK format so clients can cache and verify without the full `x5c` each time.

---

### Trust Chain Summary

```
EU Trust Anchor (root CA)
└── National CA (intermediate, optional)
    └── Registry Operator Certificate (leaf)
        └── Signs every /wrp API response
            └── Verified by Wallet Units
```
